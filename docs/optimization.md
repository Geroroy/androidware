# 성능 최적화: 다른 Android VM들의 방식과 이 엔진에 적용한 것

작성: 2026-11-12 (세션 6, 앱 0.0.17-m1, 엔진 패치 0025).
**이 문서의 수치는 전부 PC(x86_64, 4코어 컨테이너) 측정값이다. 기기(Galaxy S25 Ultra) 수치는 아직 없다.**

## 1. 결론

- 프로파일로 찾은 가장 큰 낭비는 번역된 게임 코드가 아니라 **엔진 자체**였다. 0.0.16 엔진으로 게스트가 GLES 2.0 테스트 앱을 돌릴 때 엔진 CPU 시간의 22%만 번역된 게스트 코드였고, 48%는 QEMU의 C 코드, 26%는 호스트 커널(스레드 깨우기)이었다.
- 고친 것 두 가지(패치 0025):
  1. **SEV/WFE**: 게스트 커널이 스핀락을 풀 때마다 실행하는 `SEV`를 QEMU 11이 "다른 vCPU 전부 깨우기"로 처리했다. → 멀티스레드 TCG에서는 아무 코드도 내지 않는다.
  2. **주소 공간(ASID)별 TLB 보존**: 게스트 프로세스가 바뀔 때마다 소프트웨어 TLB와 점프 캐시를 통째로 비웠다. → vCPU마다 최근 16개 주소 공간의 TLB·점프 캐시를 보관했다가 교체한다.
- PC 효과: 프로세스 왕복 전환 290~380 µs → 62~78 µs, 앱 콜드 스타트 12~18% 단축, 같은 조건의 테스트 앱 36 → 45~49 fps(§4). 4 vCPU 부팅은 87.5초(세션 2 기록은 142~150초. 그때는 Software 그래픽 구성이라 조건이 같지 않다).
- 정수·FP·메모리 벤치(순수 번역 속도)는 변하지 않았다. 게임 스레드가 자기 코드만 도는 구간은 빨라지지 않는다. 빨라지는 것은 커널·binder·다른 프로세스와 엮인 구간이다. **N.O.V.A. 3의 fps가 얼마나 오를지는 기기에서 재야 안다.**

## 2. 다른 Android VM/에뮬레이터는 어떻게 빠른가

| 계열 | 예 | 속도의 근거 | 이 프로젝트에 적용 가능한가 |
|---|---|---|---|
| 하드웨어 가상화 | Android Emulator(KVM/HVF/WHPX), Cuttlefish/crosvm, Genymotion, BlueStacks·LDPlayer(x86 PC) | 게스트 CPU 명령을 번역 없이 실행. GPU는 gfxstream/virgl로 호스트에 전달 | 불가. S25 Ultra에 `/dev/kvm` 없음, AVF는 일반 앱이 쓸 수 없음(F5). 게다가 CPU가 32비트 ARM을 실행하지 못한다 |
| 컨테이너(커널 공유) | Waydroid, Anbox, ReDroid | VM이 아니다. 호스트 커널 위에서 게스트 사용자 공간을 네이티브로 실행 | 불가. 루트와 커널 기능 필요, 32비트 실행 불가는 그대로 |
| 사용자 공간 Android-on-Android | VMOS, VPhoneGaGa, X8 Sandbox, Twoyi | 게스트 프로세스를 호스트 프로세스로 실행하고 시스템 콜만 가로챔(ptrace/seccomp), 그래픽은 호스트 GLES로 전달. CPU 에뮬레이션 없음 | 불가. 32비트 게스트는 32비트를 실행할 수 있는 CPU에서만 동작 |
| 사용자 모드 이진 번역 + 네이티브 라이브러리 | Google `libndk_translation`/berberis(네이티브 브리지), Arm Tango(32비트 앱용, 일부 제조사), Winlator·Box64·FEX, Rosetta | **앱의 코드만** 번역. 커널·libc·GL 드라이버·프레임워크는 호스트 네이티브. 간접 분기 테이블, 리턴 예측, 같은 계열 ISA면 레지스터·플래그 1:1 대응 | 구조가 다르다(방식 D). 아래 "남은 큰 것" 참고 |
| 전체 시스템 TCG | Limbo, Vectras VM, UTM SE, **이 프로젝트** | 가장 느린 계열. 게스트 커널까지 전부 번역, 메모리 접근마다 소프트웨어 TLB 검사 | 여기서 할 수 있는 것은 "번역 외의 낭비"를 줄이는 것 |
| 콘솔 에뮬레이터 | Dolphin, PPSSPP, AetherSX2, yuzu 계열 | fastmem(게스트 메모리를 호스트 주소 공간에 직접 매핑, 접근 1명령), 블록 링크, 유휴 건너뛰기, 큰 코어 고정 | fastmem은 프로세스마다 주소 공간이 바뀌는 범용 OS 게스트에는 그대로 못 쓴다 |

Android Emulator 고유 기법 중 관련 있는 것:
- **GL 명령 전달**: goldfish pipe → (신형) address space device + 공유 링 버퍼, 비동기 swap, 버퍼 직접 접근. 이 엔진은 구형 pipe 방식(MMIO 쓰기 → 유닉스 소켓)이다. 기기 실측에서 렌더러 쪽 CPU는 5% 안팎이라 지금은 병목이 아니다.
- **스냅숏 부팅**: 부팅을 한 번만 하고 메모리 상태를 저장. 게임 중 성능과 무관, 부팅 시간용. 미적용(goldfish 장치와 렌더러 상태 저장이 필요).

## 3. 측정 방법

`experiments/android-guest/perf/bench.py`(사용법은 파일 머리말). 앱과 같은 명령행(`-M virt,highmem=off,goldfish=on -cpu cortex-a15 -smp 2 -accel tcg,thread=multi`), Host GPU 모드(렌더러는 Mesa llvmpipe), 480x800, `-snapshot`. 프로파일은 `perf record -e cpu-clock`(엔진 프로세스), 횟수는 uprobe.

| 지표 | 내용 |
|---|---|
| boot | QEMU 시작부터 `sys.boot_completed=1`까지 |
| bench | `experiments/pc-tcg-aarch32/bench.c`(32비트 bionic): 정수 / FP / memcpy ms |
| appstart | Settings, Calculator 콜드 스타트 `am start -W`의 TotalTime(각 3회) |
| pingpong | `perf/ctxbench.c`: 두 프로세스가 파이프로 왕복, 깰 때마다 데이터 256쪽과 코드 64쪽을 건드림 |
| fork | 셸에서 `/system/bin/true` 150회 |

한계: 호스트가 4코어 공유 VM이라 같은 바이너리도 실행마다 ±10% 흔들린다(부팅 69.5~80초). gles2test의 fps는 llvmpipe에 묶여 있어 CPU 지표로 쓰지 않았다(엔진 CPU 사용 0.4~0.6코어).

## 4. 찾은 것과 고친 것

### 4.1 SEV가 vCPU를 계속 깨움 (적용)

- 관찰(0.0.16 엔진, 테스트 앱 실행 중): 호스트 커널 시간 26.5%. 호출 스택은 `helper_sev → qemu_cpu_kick → pthread_cond_broadcast → futex_wake`, 그리고 깨어난 vCPU 스레드가 할 일이 없어 다시 잠드는 `qemu_process_cpu_events → futex_wait`.
- 원인: Linux/ARM(3.10)은 `arch_spin_unlock()`마다 `SEV`를 실행한다. QEMU 11.1.3의 `helper_sev`는 그때마다 다른 vCPU 전부에 `qemu_cpu_kick()`을 한다. 대상 vCPU는 번역된 코드에서 강제로 빠져나오고, WFI로 쉬고 있었다면 호스트 스레드가 깨어난다.
- 수정: 멀티스레드 TCG(vCPU 2개 이상)에서는 `WFE`를 NOP으로(스핀락 대기 루프는 그냥 돈다 — WFE/SEV를 모델링하기 전 QEMU의 동작), `SEV`는 코드를 내지 않는다. vCPU 1개일 때는 `SEV`가 실제로 WFE에서 자는 CPU만 깨운다.
- 결과: 호스트 커널 시간 26.5% → 17.7%, 같은 조건(perf 부착) 테스트 앱 36.0 → 44.7~49.7 fps.
- 기기와의 관계(추정, 미검증): 기기 실측 11차의 "vCPU 0만 95%, 4 CPU로 늘리면 더 느림"은 이 동작과 맞는다(SEV 한 번에 깨우는 vCPU 수가 늘어남).

### 4.2 프로세스 전환마다 TLB·점프 캐시 전체 flush (적용)

- 관찰: `helper_lookup_tb_ptr` + `qht_lookup_custom` 등 TB 조회가 엔진 시간의 약 20%, TLB 채우기(`tlb_set_page_full`, `get_phys_addr_nogpc` 등)가 약 10%. 테스트 앱 실행 중 `contextidr_write` 426회/초, 그때마다 전체 flush. 전환 1회당 TLB 채우기 약 144회, 전역 해시 조회 약 1,100회.
- 원인: QEMU의 소프트웨어 TLB에는 ASID 태그가 없어서, 게스트가 CONTEXTIDR(ASID)를 바꾸면 TLB와 점프 캐시를 다 비운다. Android는 binder 호출마다 프로세스가 바뀐다.
- 수정: vCPU마다 (TLB 테이블, 점프 캐시) 묶음을 17개 두고, ASID가 바뀌면 지금 것을 슬롯에 넣고 새 ASID의 것을 꺼낸다(없으면 가장 오래된 슬롯을 비워 사용).
  - 페이지 단위 무효화(TLBIMVA*)는 모든 슬롯에 적용, TLBIASID는 해당 주소 공간만 버림, 그 밖의 모든 flush(TLBIALL, SCTLR/TTBCR 변경, 메모리 맵 변경 등)는 슬롯 전부를 버린다.
  - 코드 쪽 쓰기 감지(`tlb_reset_dirty`)도 슬롯까지 적용한다.
  - 슬롯에 그 주소 공간이 쓰던 TTBR0를 기록해 두고, 게스트가 같은 ASID를 다른 페이지 테이블과 쓰면 flush한다. Linux 3.10의 ASID 할당기에는 rollover가 여러 번 지난 뒤 두 프로세스가 ASID를 공유할 수 있는 버그가 있었고(업스트림 4.4에서 수정), 기존 QEMU는 매번 flush해서 이를 가렸다. PC 실행에서는 한 번도 발생하지 않았다(`info jit`의 "id reused by guest: 0").
  - EL2/EL3가 없는 CPU 모델에서 짧은 디스크립터 형식일 때만 동작한다(앱이 쓰는 구성). AArch64 게스트(Boot test)는 영향 없음.
- 결과:

| 지표 | 0.0.16 엔진 + SEV 수정 | + TLB 보존 |
|---|---|---|
| pingpong (µs/왕복) | 290~382 | 62~78 (한 실행에서만 141~147) |
| appstart Settings (ms, 3회) | 3100 / 2444 / 2158 | 2533 / 2130 / 1996 |
| appstart Calculator (ms, 3회) | 1854 / 1683 / 1519 | 1538 / 1407 / 1301 |
| fork 150회 (초) | 8.5~9.0 | 8.0~8.5 |
| bench int / fp / mem (ms) | 약 145 / 930 / 57 | 변화 없음 |
| boot (초) | 69.5~72.5 | 69.5~76 (차이 없음) |

  부팅 중 전환 66,931회 가운데 63,423회(94.8%)가 보관된 컨텍스트를 찾았다.

- 정확성 검증: `AW_TLB_CTX=verify`로 실행하면 전환이 끝날 때마다 살아 있는 TLB 항목 전부를 페이지 테이블을 다시 걸어 비교한다. 부팅 + 앱 실행 + 벤치 전체에서 **5억 2,300만 항목 검사, 게스트의 무효화 뒤에도 남은 항목 0**. 불일치 12,777건은 다음 검사 전에 사라졌고, 155건은 300 ms 넘게 남았지만 게스트가 아직 무효화하지 않은 것이었다(프로세스 종료 정리 중 — 페이지 테이블을 먼저 지우고 TLBIASID는 끝에 한 번).
- 끄는 방법: 앱 "Android 7 guest…" → "Engine: fast process switching". 끄면 이전 동작(매번 flush).

### 4.3 큰 페이지 영역 추적 (적용, 단독 효과는 미측정)

Linux는 lowmem을 1 MB 섹션으로 매핑한다. QEMU는 큰 페이지가 있는 영역을 "2의 거듭제곱 블록"으로 기억하는데, 이것이 0xc0000000부터 1 GB로 커져서 kmap(0xfff…)·vmalloc 페이지 하나를 무효화할 때마다 커널 모드 TLB 전체를 비웠다. 블록 대신 구간 [첫 주소, 끝 주소]으로 바꿨다. 페이지 무효화 주소를 표본으로 세면 0xfff… 대역이 두 번째로 많았다(가장 많은 대역 5,787건, 0xfff… 3,334건).

### 4.4 `pmu=off` (적용, 효과는 잡음 범위)

`-cpu cortex-a15,pmu=off`. 게스트는 성능 카운터를 쓰지 않는데 모델은 예외마다 PMU 처리를 한다(프로파일에서 `pmu_counter_enabled` 0.4~0.7%). 부팅·벤치 차이는 측정 잡음 안이다.

## 6. 지금 엔진의 시간 분포와 남은 것

패치 0025 적용 후(테스트 앱 실행 중): 번역된 게스트 코드 31%, QEMU C 코드 47%, 호스트 커널 18%.
- TB 조회(`helper_lookup_tb_ptr` 15% + 전역 해시 조회 약 11%)가 여전히 가장 크다. 페이지를 넘는 분기와 함수 리턴마다 조회한다. 조회 횟수를 줄이려면 리턴 예측이나 페이지 간 직접 연결이 필요한데, 후자는 주소 공간이 바뀌는 시스템 에뮬레이션에서 안전하게 만들기 어렵다.
- 호스트 커널 18%: pipe 소켓 송수신, vCPU 유휴 진입·복귀, 페이지 무효화 때 다른 vCPU 세우기(TLBI IS, 약 750회/초).
- **구조적으로 남은 큰 것**: 게임 코드만 번역하고 나머지를 네이티브로 돌리는 방식(§2의 사용자 모드 번역 + 네이티브 GL). 저장소의 방식 D(`qemu-arm` 사용자 모드)가 그 출발점이지만, Android 프레임워크·ART를 64비트 호스트에서 대신 제공해야 해서 별도 단계다.

## 7. 기기에서 확인할 것

1. 0.0.17-m1로 N.O.V.A. 3을 같은 장면에서 실행하고 Export log의 `perf:` 줄(fps, `CPU 0/TCG` %)을 0.0.14/0.0.15 기록(4.3~7.0 fps, CPU 0 94~96%)과 비교.
2. 게스트 CPU를 2 → 4로 바꿔 다시 측정. PC(호스트 4코어)에서 4 vCPU 부팅은 87.5초로 2 vCPU(약 72초)보다 여전히 느리다. 8코어 기기에서는 달라질 수 있다.
3. 이상 동작(앱 강제 종료, 멈춤)이 0.0.16에 없던 것이면 "Engine: fast process switching"을 끄고 재현되는지 확인.
