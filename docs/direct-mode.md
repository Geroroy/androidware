# 직접 모드(Direct mode): 게임 코드만 번역하는 구조

작성: 2026-11-13 (세션 7). 상태: **0단계(측정용 프로토타입) 완료, 게임은 아직 이 방식으로 실행되지 않는다.**

## 왜 바꾸는가

기기 실측(0.0.18-m1, `status.md`): N.O.V.A. 3 플레이 중 12.8~19.6 fps, vCPU 0이 74~92%(대부분 사용자 모드)로 포화. 지금 구조(방식 A, 전체 시스템 에뮬레이션)에서는 게임의 한 프레임이 다음을 전부 번역 실행으로 거친다.

1. 게임 자신의 코드
2. 게스트 GL 라이브러리가 GL 호출을 직렬화(정점 배열 복사 포함)
3. 게스트 커널의 pipe 드라이버, 인터럽트, 스케줄러
4. 메모리 접근마다 소프트웨어 TLB 검사

직접 모드는 1만 번역하고 나머지를 없앤다. 게임의 32비트 ARM 코드는 사용자 모드 번역기(QEMU `linux-user`, 이미 APK에 `libqemu-arm.so`로 들어 있음)로 실행하고, GL 호출은 번역기 안에서 **폰의 64비트 GL 드라이버를 직접 호출**한다. 게스트 포인터를 호스트 포인터로 바꿔 넘기므로 정점 배열·텍스처 복사가 없다. Google의 `libndk_translation`/berberis, Winlator(Box64)와 같은 계열이다(`optimization.md` §2).

## 0단계 결과: 같은 작업을 두 구조로 측정 (PC)

작업(`experiments/direct-mode/glbench.h`): 한 프레임에 물체 300개. 물체마다 CPU에서 행렬 계산과 정점 36개 변환(부동소수점), uniform 1회, 클라이언트 정점 배열 1회, 드로우콜 1회. 렌더 대상 64x64(PC의 소프트웨어 래스터 비용을 빼기 위해). 두 경우 모두 같은 32비트 ARM 코드이고 계산 결과 체크섬이 같다(-863.8).

| 구조 | 프레임당 시간 | 비고 |
|---|---|---|
| A: Android 7 게스트 안의 앱(엔진 0025, Host GPU 모드, 2 vCPU) | **43.8~47.9 ms** | 게스트 GL → goldfish pipe → 렌더러 프로세스. 프레임마다 SurfaceFlinger를 거치는 swap 포함(물체 1개짜리 프레임도 PC에서 약 25~27 ms) |
| 직접 모드: `qemu-arm` + 호스트 GL thunk | **1.42~1.54 ms** | 같은 프로세스에서 호스트 GL 직접 호출, swap은 pbuffer |

- swap 경로 차이를 빼고 물체당으로 보면 A는 약 65 µs(300개에 약 20 ms), 직접 모드는 약 5 µs로 **약 13배**.
- 이 수치는 PC(x86_64, 호스트 GL은 Mesa llvmpipe)다. **기기 수치는 아직 없다.** 0.0.20-m1의 "Engine self-test"가 같은 작업을 기기에서 직접 모드와 네이티브 64비트로 실행해 `glbench: … ms_per_frame=…`을 출력한다(PC에서 x86 빌드로만 시험, Android 빌드는 미실행).
- 이것은 GL 호출이 많은 합성 작업의 결과다. 게임 로직 자체(순수 번역 속도)는 직접 모드에서도 네이티브보다 느리다: 기기 실측으로 사용자 모드 번역은 네이티브 대비 정수 1.9배, FP 6.6배, 메모리 3.6배 느리다(전체 시스템 모드는 2.1 / 7.4 / 14~17배).

## 60 fps가 나오는가

모른다. 근거가 되는 것과 아닌 것:
- 유리한 점: GL 경로와 커널 경로가 사라진다. 게임 스레드에 남는 것은 게임 코드의 번역 실행뿐이다.
- 불확실한 점: N.O.V.A. 3의 프레임 시간 중 게임 코드 자체가 차지하는 비율을 모른다. 그 부분은 약 2~7배 느린 번역 속도 그대로다.
- 3단계가 끝나 게임이 이 방식으로 떠야 실제 fps를 잴 수 있다.

## 구현 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 0 | thunk 메커니즘(게스트 스텁 `svc 0x9f0100` → 번역기의 `aw_thunk_call()` → 호스트 EGL/GLES), 측정 | 완료(엔진 패치 0026, GLES 함수 26개만) |
| 1 | 번역기를 앱 프로세스 안에서 라이브러리로 실행. 게스트 동적 링커 + bionic(Android 7 이미지의 `/system/lib`)로 게임 `.so` 로드, "게스트 함수 호출" API, 스레드. GLES 1.x/2.0·EGL·`libandroid`·`liblog`·OpenSL ES 전체 thunk(스펙에서 생성) | 미착수 |
| 2 | JNI 다리: 게임 `.so`의 `JNI_OnLoad`/네이티브 메서드를 호스트 ART에 등록하는 트램펄린, 게스트용 `JNIEnv` 함수표(약 230개), 64비트 객체 참조 ↔ 32비트 핸들, 콜백 재진입 | 미착수 |
| 3 | 게임의 Java 코드(dex)를 이 앱 안에서 실행: Activity 대리 실행, 게임 APK의 리소스·에셋, OBB 경로 연결, 2012년 API와 Android 16의 차이 메우기 | 미착수 |
| 4 | N.O.V.A. 3 구동, 성능 측정, 검은방 | 미착수 |

## 위험 (단계를 막을 수 있는 것)

- **3단계가 가장 불확실하다.** 설치되지 않은 APK의 Activity를 호스팅하는 것은 공개 API가 아니다(VirtualApp류 기법, Android 16의 숨김 API 제한). 2012년 Gameloft Java 코드가 Android 16 프레임워크에서 그대로 도는지도 미지수다.
- 번역기와 ART가 한 프로세스에 공존: SIGSEGV 처리 충돌, 32비트 게스트용 주소 공간 예약, JIT용 실행 가능 메모리.
- 게스트 bionic(Android 7)이 Android 16 커널·속성 영역 위에서 초기화되는지(정적 링크 바이너리는 기기에서 확인됨, 동적 링크는 미확인).
- 방식 A는 그대로 유지한다. 직접 모드가 막히면 A가 남는다.
